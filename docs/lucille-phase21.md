# Lucille Phase 2.1 — partial, isolated semantic-learning implementation

This phase is **not fully validated**. No authorized running isolated Gemma 4 or Nomic service was established. No operational service was started, stopped, unloaded, reconfigured or queried for inference. No weights, launchers, private profiles or real chats were imported. The implementation and tests below use fictional data and explicitly simulated protocol responses/vectors. These do not measure Gemma extraction quality or Nomic embedding quality.

The base is Phase 2, `c4a401b55d8f7231351039a744c861344c4a4cab`. The initial remote check and later audit confirmed PRs #1–4 open, draft and unmerged. Branch: `feature/lucille-phase21-semantic-learning`, stacked on `feature/lucille-phase2-intelligent-memory`. No merge, release, operational install or general activation is authorized.

## Reused architecture and changes

The existing SQLite Store, migrations, FTS5, extraction_jobs, leases, retry limits, policy, Claim/ingest, provenance, quality, revisions, tombstones, versioned vector spaces, retrieval filters and management UI are retained. There is one canonical database and one ingest boundary. The existing Chat/Agent/Code canonical-user adapter and native-writer fences remain in place.

Migration 005 adds `learning_inputs` to the existing extraction queue, not another job system. Only eligible LLM/hybrid jobs retain at most 1,600 bytes of the user message, without conversation history. A terminal-state trigger purges that source on completion, cancellation and final failure. Logical backup schema 5 preserves it transactionally; schemas 2/3/4 remain importable. Invalid retained sources or terminal-source combinations fail restore. Imported leases are revoked by the existing backup rules.

New profiles still default to disabled learning and `rules`. An explicit settings action selects `rules`, `llm` or `hybrid`; disabling or switching modes cancels pending/in-flight jobs and purges their sources. The native rule worker claims only jobs without an LLM input. The single frontend LLM runner claims the other jobs through native IPC, uses the existing configured ProviderClient/chatWithTools interface, and returns proposals to Rust for deterministic validation and transactional ingest. It does not receive a SQLite connection or permission to write claims directly.

The background runner waits while any primary generation is active, aborts when primary generation begins, bounds the call to 12 seconds/768 output tokens, passes no tools and does not change a model context setting. It makes one application extraction call per eligible turn; provider-level transient retries remain subject to that deadline. The three-attempt queue and 30-second lease remain authoritative. Native completion rechecks stored evidence, scope, current policy and token inside the transaction. Failure uses the database attempt count, ignoring a forged caller count. Hot-reload disposal cancels the runner during development.

Only already configured, enabled, unmanaged local validation routes are eligible. The shipped full QA host still denies network destinations beyond the dedicated mock; no operational/cloud provider or managed-model lifecycle is invoked. No endpoint availability or Gemma weight identity is inferred from a selected alias. A live configured backend and host authorization must be supplied and validated before this can be called a real Gemma integration.

## Structured output and false-memory boundary

The response schema rejects extra keys and includes kind, content, entity, property, value, scope, project, temporal class, verbatim evidence, correction/hypothesis flags, confidence and relevance. Limits are four proposals and 12 KB of response text. Evidence must be a complete verbatim sentence/span at the declared sentence boundary, up to 300 bytes. A model cannot remove a negation by selecting only a positive subphrase.

Exact evidence is necessary, not proof of semantic entailment. Supported known topics are independently interpreted by the deterministic extractor; incompatible content, values, temporal interpretation, corrections or project hints are rejected. The LLM can additionally propose extractive, direct first-person game-class/progression preferences with separate topic keys and exact value spans. Those novel claims have a fixed conservative confidence below the autoapproval floor, so they remain candidates. Known clear preferences can still promote when the configured conservative policy is satisfied. Model confidence cannot increase validator certainty.

Quoted, third-party, fictional, forwarded, hypothetical-question, identity/permission-changing and supported sensitive/ironic forms are excluded conservatively. Unsupported semantic assertions abstain. This is a deliberately limited verification ontology, not a general factuality, irony or secret detector. It cannot establish truth for arbitrary natural language. General paraphrases and ambiguous device references remain incomplete; the frozen evaluation's misses are preserved. No automatic high-impact update or invented equipment identity was introduced.

Hybrid mode combines accepted proposals with independently grounded rule claims and deduplicates by canonical claim fingerprint, with at most four total candidates. A transport/rejection failure can complete only the verified rule part in hybrid mode; LLM-only work retries/fails. An expired or cancelled completion is not shown as a successful write. All accepted claims then use existing conflict suspension, explicit replacement approval, reversible history and deletion/tombstone behavior. Related classes/progression preferences stay separate instead of being forced into one tactical-game preference.

## Embedding client, identity and fallback

The new HTTP client uses the existing localFetch/native-proxy transport with OpenAI-shaped `/v1/embeddings` responses. It checks a full manifest before and after encoding, exact model and response identity/index, dimensions, finite unit vectors, byte/context ceilings, document/query prefixes, pooling, normalization, revision/fingerprint and index version. Native Store validation and memory-version checks remain the final index boundary.

An advertised model name/fingerprint is **not weight attestation**. The current validation transport permits only an explicitly marked synthetic manifest. It rejects a response claiming to be real without weight attestation. The fixture model label is Nomic Embed Text v1.5, but revision is `SYNTHETIC-NOT-NOMIC-WEIGHTS`, fingerprint is a test sentinel, dimension 64, mean pooling, L2, `search_document: `/`search_query: ` prefixes and an 8,192-byte conservative ceiling. No real Nomic weights were used. The closed test contract is not proof that a real server applies those transforms.

The Settings button explicitly builds a **simulated** index for up to 64 current scoped memories. Retrieval reads the active manifest and obtains a query vector; endpoint/identity/shape failures fall back to FTS5. Retrieval does not write vectors. Index status reports `transport_verified=false`. Memory edits, deletion and incompatible space changes retain existing invalidation/version checks. Scope, project, state, conflict, expiry, diversity and context-budget filters apply after semantic ranking as well as lexical ranking.

Real Nomic integration still requires an isolated endpoint/authentication contract, independently hashed weights/revision and provenance, effective dimensions/pooling/normalization/prefixes/tokenizer/context, and CPU/RAM/VRAM validation on the target machine. No operational port 8128 was contacted. The [official Nomic model card](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5) remains the expected model contract; a fixture does not establish real-model compliance. No second model instance was started.

## Frozen evaluation and comparisons

Acceptance limits were written before implementation in `lucille-phase21-acceptance.md`: extraction precision >=95%, recall >=80%, zero unsafe writes/scope errors/current duplicates/stale retrieval; retrieval precision >=90% and recall >=80%, with independent reporting of synthetic and real runs. The initial evaluation was hashed before code changes and copied unchanged for repeatability. Audit found two initial examples later reused in development tests, so it is not presented as fully independent. Its original results are preserved. SHA-256: `46130605357e9b797832f3479a14227742eb5cd240df58f9055df16dbbdf588f`. It contains 20 cases spanning informal/formal Portuguese, English, typos, paraphrases, negation, irony, changes, third-party/fiction/forwarded text and attacks. It is a small predeclared synthetic set, not a statistically representative unseen real-world corpus.

On those 20 cases, the Phase 2 rule baseline produced 4 correct extractions, 0 false positives and 6 misses: precision 1.0, recall 0.40 on 10 eligible statements. Per-category/language counts and all six failures are retained in the machine-readable result. This fails the new recall gate and was not tuned away. Phase 2.1 real-LLM precision/recall, correction detection, tokens, latency, RAM and VRAM are **null / not measured**, since no real endpoint was used. The scripted model is a development protocol fixture, not the evaluation oracle or a claimed Gemma result. Defaults remain off; no broad rollout is justified.

A second 20-case evaluation was sealed after the production extraction algorithm was frozen, without overlap with the scripted extractor or pre-freeze development examples: SHA-256 `3974a1f5b1c251d0ce915ee1a7ea6e524a2e446e73a9b1212d5c713d4eac7ee1`. It is not used by the scripted extractor. The original Phase 2 extractor from the base commit is retained verbatim as a **test-only reference**, not a runtime writer or memory system, to compare the same independent inputs. On the same second set, the exact Phase 2 reference produced 7 true positives, 2 false positives and 3 misses (precision 0.7778, recall 0.70). Current rules produced 7 true positives, 0 false positives and 3 misses (precision 1.0, recall 0.70). The forwarded-message false positives are eliminated, but recall still fails the 0.80 gate. Reports preserve both reference and current-rule failures/counts; real Gemma/Nomic metrics remain null. No extraction algorithm is adjusted after opening this second set. Do not compare recall percentages across different datasets as an improvement claim.

A separate three-query synthetic-vector ablation measures the ranking mechanics: lexical precision 1.0/recall 0.50; semantic and hybrid precision 1.0/recall 1.0, with zero false positives. Hybrid ties semantic here; this does not establish that hybrid beats semantic or that Nomic performs this way. Synthetic vectors encode explicit fixture concepts, and the query set is tiny. A real embedding ablation with broader held-out data remains required.

## Validation and limitations

Core tests cover persistent LLM jobs, lease fencing, hybrid idempotency, complete-sentence grounding, scope/schema/value attacks, separate preference facets, cancellation, mode changes, terminal purge, backup/restore, SQLite failure rollback and forged failure counts. Frontend tests cover route refusal, primary-generation scheduling/cancellation, one bounded provider call, fallback and malformed/drifting/unattested embedding responses. Prior memory/identity/native-writer tests are retained.

The complete isolated GUI exercises Chat/Agent/Code through their real composers and hooks, four simulated extractor calls for four eligible interactions, hybrid deduplication, candidate facets and a paraphrase retrieved through a real native vector index with synthetic vectors. The UI shows extraction mode, processing, candidate/conflict/failure counts, simulated LLM status, simulated embedding identity/index and lexical fallback. It does not display these as operational Gemma/Nomic integration. Existing full-app filesystem/staging/approval/refusal regression remains part of validation.

Native reopening uses a verified, scheduled synthetic LLM queue fixture imported through the transactional backup API. The entry is confirmed queued before shutdown; after reopening/hydration it must become done, preserve identity/binding/provenance, purge input and issue exactly one simulated extractor request. The reopening scripts use explicit bounded polling of resolved IPC state; an earlier asynchronous test predicate advanced too early and was corrected. No claim of a real-model restart is made.

All execution remains in the marked checkout-owned root, dedicated WebView/cache/workspaces and loopback test ports. Native Windows screen capture is not repaired; own-WebView inspection supplies autonomous screenshots. Windows 10/i7-3770 host execution introduces no AVX2 flags, but real Nomic/Gemma CPU compatibility and resource costs are unmeasured. Gemma's operational 65,536-token configuration is untouched. No operational model was loaded, replaced or unloaded.

GitHub CI must be reported for the final exact HEAD. The previous HTTP 422 block is not assumed resolved; branch/base filters retain all gates/pinned actions. No administrative change, merge or release is performed. Full completion remains blocked on authorized isolated live models, independent weight/config attestation, real extraction/embedding evaluation meeting the fixed thresholds and mandatory remote checks.
