# Lucille Phase 2: conservative intelligent memory

This development branch is stacked on Phase 1.6 (`7174f3393c64caace50257583b2c56d8661ec75c`). It retains the isolated **debug-only** host, explicit Lucille binding, fictional profiles and SQLite/FTS5 canonical store. The installed application, real conversations, providers, model files, operational ports and 65,536-token Gemma configuration are not migrated or modified. Learning defaults to **off**, including after an old-schema migration. Native memory still works for other personas.

## Data and execution

Migration `004_intelligent.sql` adds a persisted learning policy, extraction jobs, quality/temporal metadata, provenance, reversible revisions, deletion digests, embedding-space manifests and versioned vectors. Existing records, identity, FTS triggers and retrieval audit survive. Logical backup schema 4 includes this state; schemas 2/3 remain importable. Restore is transactional, validates fixed tables and parameterized values, and revokes imported leases. A corrupt or unsupported backup rolls back.

After a finished durable Chat, Agent or Code turn, a fire-and-forget adapter refetches the conversation and checks explicit binding, canonical preceding user text, successful assistant completion and cancellation. Assistant/tool output, generated slash/report text, hidden messages, remote/group sessions and expanded attachment text are not extraction evidence. Regeneration carries the original user interaction ID; the content hash distinguishes edited source text. Model tool catalogs cannot call these management commands. Bound paths bypass native retrieval/extraction; unbound behavior remains available.

The native host starts at most one worker. Jobs use SHA-256 of conversation, canonical user ID, scope, project and text hash. A transactional claim receives a 30-second UUID lease; commit checks the actual stored scope/evidence/token, not a caller's claimed confidence. At most three attempts are allowed, with bounded backoff, expired-lease recovery and cancellation fencing. Evidence is removed on completion, cancellation or terminal failure. Disabling learning cancels queued/running/retry jobs. Reopening waits for chat-store hydration, then wakes pending work when a Lucille binding exists. Terminal IDs remain for idempotency; this is not an unlimited conversation archive.

Resource ceilings: 16,000 UTF-8 bytes per extraction input, four proposals, at most 300 bytes of evidence per proposal, at most 64 pending jobs, one worker, three attempts, 12 returned memories and the existing per-turn context budget. Automatic topic reconciliation inspects at most 500 related/unclassified records and fails closed above that capacity. The synthetic vector baseline scans at most 1,024 scoped vectors. It is deliberately not an ANN index for large collections. Durable records have no access-frequency expiry.

## Extraction and approval

The initial extractor is a bounded PT/EN rule baseline, with **no LLM call or extra loaded model**. It supports explicit coffee/language/tactical-game preferences, installed/free RAM, project database choices, goals, dated tasks, constraints, solutions and hardware hypotheses. All 11 existing categories remain available for manual management; unsupported facts and summaries abstain. This does not claim general natural-language extraction or comprehensive secret detection. Quoted/third-party/sensitive/permission-changing statements are conservatively skipped. Ambiguous “8 GB free” without a RAM qualifier is skipped rather than assumed to describe RAM.

Only clear, non-sensitive, conflict-free preferences can automatically activate, when the user enables learning and preference promotion. Confidence >= .96 and relevance >= .8 are required in addition to verified evidence and an allowed rule/category. These numbers describe extractor certainty, not truth. Hardware, decisions, tasks, goals, hypotheses and all conflicts wait for review. The UI can disable preference autoapproval independently.

Entity/property/value metadata catches RAM corrections across “PC”, “computador” and “instalei”, while distinguishing the primary computer, another computer and the work laptop. A new conflicting value creates a replacement candidate and suspends earlier contradictory context. A clear current-message correction suppresses the old value even before asynchronous extraction finishes. Approval checks the prior version the reviewer saw, atomically obsoletes it, and rejects remaining active contradictory claims. Unknown equipment identities and unsupported paraphrases require manual review; this is not unrestricted entity resolution.

Equivalent preferences consolidate only within the same scope/project/topic and compatible value. Tactical-game facets preserve RPG, classes and progression, with separate minimal provenance. Distinct coffee/language/game topics do not merge. Content changes preserve revision snapshots and increment versions. Restoring a revision checks current versions and active-topic conflicts. Deletion erases content, provenance, vectors and revisions; a digest tombstone prevents automatic relearning of that same known claim. Historical messages already sent to a model are not rewritten.

Temporary RAM observations expire after one hour; dated tasks after two days; hypotheses after seven days. Installed capacity, durable goals and preferences do not expire merely because unused. Expiry excludes retrieval and remains visible for review; it does not silently delete the record.

## Retrieval and semantic boundary

FTS5 works independently of a model/embedding endpoint. Query tokens are escaped, common stopwords removed and a small explicit alias set applied. Selection filters scope, project, active state, expiry, unresolved topic conflicts, equipment identity and intention, then combines lexical/semantic scores with small bounded priority and temporary-recency adjustments. It removes equivalent topic/content results, respects context limits and caps preference cost at a quarter of available context. It does not inject a general preference merely because that preference exists. Explicit recall requests may list relevant active records.

The identity policy asks the assistant to use relevant memory quietly. Provenance phrases remain appropriate when the user asks what is remembered or source attribution matters. There is no blind phrase prohibition. Payload tests prove selection, not fluent or natural generation.

`EmbeddingClient` has no instantiated network implementation. A manifest includes exact model, revision, SHA-256 fingerprint, dimension, normalization, pooling, prefixes, context ceiling and index version. Query/document wrappers check the manifest before and after encoding, distinguish prefixes, reject oversized inputs and nonfinite/nonunit vectors, and tie vectors to current memory versions. Any manifest change invalidates the index, even with equal dimensions. A stale space falls back to FTS.

The [Nomic Embed Text v1.5 model card](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5) specifies task prefixes, mean pooling, a native 768-dimensional representation and an 8,192-token context; its Matryoshka example applies layer normalization, truncation and L2 normalization. The manifest validates supported dimensions and `search_query: `/`search_document: ` prefixes for that exact model. This is preparation, not a claim about an existing server. No safe isolated live endpoint was established: actual endpoint/authentication, effective GGUF/model identity and fingerprint, tokenizer/context behavior, vector transformation and CPU/RAM/VRAM costs remain **unverified**. No request or configuration change was made to operational port 8128. Real Nomic embedding inference remains pending.

## Validation and honest limits

Acceptance gates were written in `lucille-phase2-acceptance.md` before benchmark tuning. The frozen extraction fixture contains 46 cases (24 supported eligible declarations and 22 cases that should abstain). The first run found three false positives: third-party hardware, a negative ownership statement and fictional hardware. These cases stayed in the fixture while the implementation was corrected. Extra regressions cover negated preferences, forged leases, bank failures, concurrent connections, stale vector versions and corrupt backups.

The retrieval fixture contains 12 queries: seven expected memory results and five unrelated queries. The benchmark reports precision/recall, irrelevant injections, duplicates, scope errors and extraction p95 timings; tests separately exercise corrections, conflicting equipment, expiry, project isolation, deletion, budget ceilings and durable reopening. Passing this small fixture is not evidence of broad linguistic coverage. Real-generation unnecessary-memory-reference rate is **null / not measured**. No real inference model was loaded, and no real-generation naturalness claim is made.

Reproduction uses `cargo test --locked --manifest-path crates/lucille-memory/Cargo.toml`, the real SQLite synthetic bridge, focused Vitest/native-memory regressions, application and QA TypeScript, changed-file ESLint, production/QA frontend builds and both isolated Windows native hosts. Set test TEMP/TMP and CARGO_TARGET_DIR inside the checkout's dedicated work directories. For full-host builds set TAURI_CONFIG to `src-tauri/tauri.lucille-validation.conf.json`; **clear that environment override before compiling the separate Phase 1.5 QA crate**, which has its own context and icon path.

The launcher/stop scripts retain exact executable/PID/root checks, dedicated WebView data, deny-by-default commands/network, and loopback 15283/15284/15287. `test-lucille-phase2.mjs` drives real composers/hooks, Settings controls and native IPC/SQLite. `test-lucille-full.mjs` retains approved filesystem/staging/refusal regressions. All model responses are explicitly simulated. Autonomous screenshots use only the test WebView; native Windows capture is not claimed repaired. Windows 10/i7-3770 native execution is exercised without introducing AVX2 flags. Linux execution and actual model resource costs remain unverified locally.

GitHub Actions remains a separate blocker: read-only API inspection reports enabled=true/allowed_actions=all and active workflows, while explicit workflow dispatch previously returned HTTP 422 “Actions has been disabled for this repository.” No administrative permission changes or weaker gates are applied. New branch/base filters retain all security checks and pinned actions. The draft PR must report fresh dispatch/check status for its exact HEAD; absent runs are **not green CI**.
